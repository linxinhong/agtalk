# 图工程：把长推理改造成执行图

> **写作时间**：2026-08（本会话环境无法联网，文中厂商能力信息基于写作时的公开认知，**未二次核实**；发布或引用前请复核各厂商官方文档，尤其 4.2 Claude Code Dynamic Workflows 的 API 细节与 4.3 Agent Teams 的稳定性标注）。
> 作者视角：本文第一手实践来自 agtalk（本地 Agent 对话总线）的图工程子系统（`docs/design_graph.md`），已实测跑通"提交 → 并行派发 → worktree 隔离 → 验证 → commit → merge → 恢复"全链路。

## 0. 词汇表（先读）

| 词 | 定义 |
|---|---|
| **节点（Node）** | 执行图中一个可独立调度的最小工作单元（"改后端 API"、"跑测试"、"人工审批"） |
| **边（Edge）** | 节点间的依赖/触发关系：`on_success`（成功才继续）、`on_failure`（失败触发修复/补偿） |
| **状态（State）** | 节点运行状态机（pending → ready → running → verifying → succeeded / failed / blocked …），驱动恢复与重试 |
| **门禁（Gate）** | 节点的验收条件（路径白名单、artifact 校验、schema、命令检查）；不满足则节点失败，不进入下游 |

## 1. 核心论点：图工程的价值在质量，不在并行提速

LLM 的"长推理"有三个固有弱点：**不可分解**（一次对话吞下全部上下文）、**不可隔离**（一次失败污染整个任务）、**不可验证**（输出没有客观验收）。图工程把长任务显式改造成 **可分解 / 可隔离 / 可并行 / 可验证 / 可恢复** 的执行图：

- 可分解：DAG 显式表达"谁依赖谁"，上下文按节点裁剪，而不是全量塞给一个 agent；
- 可隔离：写节点在独立 worktree/workspace 执行，互不污染（并行开发同一仓库的两条分支）；
- 可并行：互不依赖的节点并发派发（实际提速是副产品）；
- 可验证：每个节点的产物过门禁（路径/artifact/schema/命令），**造假会被留证**；
- 可恢复：节点失败级联 blocked、可重试新 attempt、可挂修复子图（on_failure）、lease 过期探测续活。

**为什么说价值在质量**：并行提速有限（依赖链的串行段决定总时长），而质量收益是结构性的——错误被门禁挡在局部，不会一路污染到最终产物；失败现场保留，可诊断可回滚。评测时应先看"图完成后的产物可信度"，再看"墙钟时间"。

## 2. 核心抽象：四元组（节点 / 边 / 状态 / 门禁）

1. **节点类型**：executor（agent 执行）、deterministic（脚本/命令）、join（汇聚）、gate（分叉控制）、approval（人类审批）。
2. **边语义**：`on_success`（主流程）；`on_failure`（失败激活修复/补偿分支）；纯 on_failure 分支在依赖成功时被 blocked（condition_not_met），在失败时激活——这是"修复子图"的机制基础。
3. **状态机**：乐观锁推进（version +1），非法迁移拒绝；收敛规则（converge）在节点全部 terminal 时推导图终态，daemon 重启后按状态机恢复现场。
4. **门禁**：接受条件（acceptance）在派发消息中随节点下发；候选结果需过路径白名单（write_paths ⊆ 修改、forbidden_paths ∩ 修改 = ∅，叠加 symlink canonicalize 防护）、artifact 存在性 + checksum、schema 校验。

## 3. 六个支柱（agtalk 实践基线）

| 支柱 | 实现要点 |
|---|---|
| 分解 | spec（YAML）声明节点/边/workspace/验收；编译期做结构校验（环、孤立节点、依赖缺失）与契约校验（必填项） |
| 隔离 | 写节点按 `git worktree` 隔离（`<repo>/.agtalk/worktrees/<run>-<node>`）；无 git 时降级并显式记事件 |
| 并行 | 调度器按 max_concurrency 派发；同一轮跳过有写冲突（write_paths 相交 / 共享契约文件 / 同 workspace）的节点 |
| 验证 | 路径 + artifact（sha256）+ schema 三层；验证记录（verifications）结构化落库留证 |
| 恢复 | 失败分类（path_violation / contract_violation / agent_timeout …）决定是否自动重试；lease 过期先发探测消息、grace 内等 agent 心跳续活；daemon 重启 reconcile |
| 审批 | approval 节点复用人类审批链（msg ask），节点进入 waiting_approval，回复/取消推进状态 |

### 4.1 抽象层级提示（先读）

"图"在 AI coding 语境有两种含义，**不要混淆**：

- **运行时推理图**（本文主题）：任务在执行中被拆成可调度节点，节点间依赖由运行时解析（Claude Code Dynamic Workflows、Codex Agent SDK 的编排、agtalk 图工程）；
- **工程流程图**（编排产物，非运行时）：以 issue/PR 为节点的流程表达（GitHub Copilot 的 workspace/epic），描述"工程活动怎么串"，节点不是推理子任务。

下面对比只针对第一种；Copilot 列在 4.5 并明确标为第二种。

### 4.2 Claude Code：Dynamic Workflows（最佳实践案例）

- **机制**：JS 编排运行时（task script）定义节点与依赖（`describe_task` / `startTask` / `NodeResult`）；子任务可并行，父任务按 `dependencies` 聚合结果；节点内是普通 Claude Code 会话。
- **定位**：把"长任务"显式改写为可并行/可检查的任务图——与本文论点一致（质量 > 提速）。
- **核实提示**：API 细节（`NodeResult` 字段、`startTask` 参数、失败传播）迭代很快，**发布前必须对照当前官方文档复核**。

### 4.3 Claude Code：Agent Teams（实验）

- **机制**：多 agent 并行编排（自定义角色 agent + 任务分派）；标注为实验能力。
- **与 Dynamic Workflows 的分工**：Teams 偏"多角色并行协作"，Workflows 偏"结构化任务图"；两者可叠加。
- **稳定性**：实验状态，生产使用需自行评估。

### 4.4 OpenAI Codex：Agent SDK 的编排原语

- **机制**：Agent SDK（Responses API 之上）提供 agent 与 handoff/交接原语——多 agent 以"交接链"而非"依赖图"组织；`tracing` 支撑可观测。
- **差异点**：Codex 的图能力更偏向"链式交接 + 工具内聚"，缺少显式的节点门禁（验收条件）与状态机恢复，这是与 Dynamic Workflows / 本文框架的机制差距。

### 4.5 GitHub Copilot：工程流程图（抽象层级不同）

- **机制**：以 issue/PR 为节点的工程流程（Agent 模式执行、epic 组织批量任务）——**属于 4.1 的第二种"图"**：表达工程活动序列，不表达推理子任务的依赖/门禁。
- **结论**：不是运行时推理图的对标物；与 4.2–4.4 放在同一张对比表会产生"图"的语义混淆。

### 4.6 Gemini CLI / Cursor

- **Gemini CLI**：任务执行型 CLI，原生多 agent 编排能力弱；Google 侧更值得关注的是 agent 间协议（A2A）方向，非 CLI 内建图编排。
- **Cursor**：后台 agent / 多 agent 并行有产品迭代，但**没有公开的任务图/门禁抽象**——并行是调度实现，不是用户可声明的图模型。

### 4.7 对比小结

| 工具 | 图模型 | 门禁（验收） | 状态恢复 | 抽象层级 |
|---|---|---|---|---|
| Claude Code DW | 显式任务图（JS runtime） | 部分（节点结果检查） | 有（重试/恢复） | 运行时推理图 |
| Codex SDK | 交接链 | 弱（无显式验收） | 部分 | 运行时推理图 |
| Copilot | issue/PR 流程 | 无（靠 CI） | 无 | **工程流程图** |
| Gemini CLI / Cursor | 无公开图模型 | 无 | 无 | 调度实现 |
| **agtalk 图工程** | 显式 DAG + 状态机 | **完整**（路径/artifact/schema/命令） | **完整**（乐观锁/探测/重试/修复子图） | 运行时推理图 |

## 5. 成本决策规则：何时不值得上图

图编排有固定开销（spec 编写、编译校验、调度、恢复逻辑——agtalk 实测单图编排开销约为直接单 agent 的 **20 倍**数量级，主要指调度/验证/工作区管理，不含推理成本）。**至少满足一条才值得上图**：

1. **可并行度 ≥ 3**：至少 3 个互不依赖、不共享可变状态的子任务（并行收益覆盖编排开销）；
2. **任务时长 > 30 分钟** 且中途失败代价高（长任务需要恢复点，不能全量重来）；
3. **验证可自动化**：有确定性验收（test / build / lint / schema），门禁能客观拦截；
4. **需要人类审批门禁**：存在风险环节（发布、敏感变更），必须人工确认。

**明确不值得上图**（走单 agent）：

- 任务 < 5 分钟、无并行、无验证、无审批；
- 子任务强耦合共享可变状态（无法隔离，图会变成伪并行）；
- 验证只能人工判断（门禁无法自动化，恢复失去依据）。

## 6. 结论

图工程不是"让 agent 更快"，而是"让 agent 更可信、更可恢复"。它的价值主张：**错误被门禁挡在局部、失败有现场可诊断、人类在关键节点把关**。选择工具时，先看它有没有显式的图模型与门禁抽象，再看并行能力——没有门禁的"并行"只是调度优化，不是图工程。
